## 3. Capture paths already in place (requirement 2, 4, 11)

- **MemoryProxy routing already captures skill extraction events.** Both LLM pipelines
  (`pipeline/runners/openai-chat.ts`, `pipeline/runners/anthropic.ts`) and the
  `archive` + `mem-command-intercept` stages call `triggerSkillExtractIfReady`
  (handler-glue) after every turn; the turn is normalized to the core's 5-role schema and
  POSTed to `/v3/skill/conversation/add`. The core buffers per agent/team/task
  (`SkillBufferStorage`, sub-path `skill_buffer`) and its background worker
  pool (`skill-pool-default-7`, seen emitting worker logs in `docker logs`)
  does extraction off the critical path.
- **OpenChamber capture path**: OpenChamber traffic flows through the tdai-proxy lanes
  (`/claude-code/*`, openai lanes), so it inherits the same per-turn capture — no new hook
  needed.
- **Claude Code capture path**: main-agent routing already points Claude Code at the proxy
  lane (verified earlier: proxy routing present in `~/.claude/settings.json`), plus the
  installed SessionStart/SubagentStop memory hooks for bounded recall. Skill extraction rides
  the proxy lane, not the hooks.
- **Duplicate-extraction risk (validation #8)**: by design there is only ONE extraction path
  — the core worker on the conversation buffer. The direct `/v3/skill/extract` trigger is
  deliberately NOT wrapped by the proxy client (core-client.ts wraps only search, listing,
  conversation/add and force-archive "on purpose"), and the plugin `/v3/skill/raw` path is
  load-only. A duplicate-capture demonstration will be a config/consistency check, not new code.

## 4. Recall, versioning and isolation already shipped (requirements 6–10 partially)

- **Versioning**: core has head/version semantics (`is_head`, head never deleted,
  `getHeadIncludingArchived`, versions endpoint) → version-checked patches (requirement 8)
  map onto `/v3/skill/patch|update` + `versions`.
- **Status model**: `SkillStatus = "active" | "archived"` (`types.ts:236`); archived head is a
  soft delete invisible to normal reads. Version pinning: the proxy lazy-pins the first-seen
  head version per session (HSETNX semantics) so an in-flight session keeps a consistent view.
- **Isolation (requirement 9)**: proxy precomputes a team-visible skill-id whitelist and
  filters `/search` envelopes (`filterTeamSearchResponse`); owner listing (`/v3/skill/list`)
  includes private skills only for the owner path; proxy `headerAutoSelect` carries
  team/agent/task identity headers.

## 6. Gap that is actually missing (requirements 6, 5)

The deployed core has **no verification gate between auto-extracted draft and active skill**:
extraction publishes head versions directly `active`, and the only governance is the
proxy's *who-may-see* whitelist — not *what-is-verified*. This is the single smallest missing
piece: an explicit gate that reviews newly auto-extracted skills against task/tool evidence
before they may serve as active agent instructions, and archives what fails — reusing the
selflearn evidence/verification mechanics rather than inventing a parallel pipeline.

## 7. Minimal implementation plan (smallest diff)

1. **`scripts/skill-gate.mjs`** (new, ~1 file): runs between sessions alongside the existing
   `memory_promote.py` cadence (same runbook docs; no new scheduler — requirement 13).
   - list recent auto-extracted skills via `memory_client` (`/v3/skill/list`);
   - for each: locate its source session evidence (conversation provenance from the archive
     envelope), cross-check tool/validation evidence through `selflearn-candidates.mjs`
     primitives (`sanitizeEvidence`, `dedupLesson`, `recordVerification`) and RepoQL
     (`rql explore/read`);
   - **verified → leaves the skill `active`** (optionally `patch`es it with a provenance
     note + version bump when the procedure needs correction — requirement 8);
   - **unverified → `patch status: archived`** with a reason string (reversible: un-archiving
     is a later versioned patch);
   - writes one append-only outcome ledger per run under `data/skill-gate/` (hash-chained,
     like the doc-ingest ledger) — keeps stateless idempotency and makes the
     "cannot publish/unverified" demonstration concrete.
   - duplicates (same normalized title/steps) → archive the newer, keep the older (core store
     + gate ledger check; mirrors `dedupLesson`).
2. **Wiring (no new framework):** the Claude Code `Stop` doc-hook kind already runs a
   closeout stage; the gate runs in the same between-session slot as `memory_promote.py` —
   i.e. documented as step 0 of the existing promotion cycle in
   `docs/memory-capture-promotion.md` (1-line doc change), NOT a new hook, timer or daemon.
   Background extraction stays in the core's worker pool (unchanged, requirement 11/12).
3. **Recall in new sessions (requirement 10):** unchanged — the proxy's skill injector already
   injects matching active skills with bounded `topK` (20 → per request envelope slice), and
   `/skill-bridge/v3/skill/raw` serves bounded client-side loads. The gate only changes WHICH
   skills are eligible (verified-active only).
4. **Validation demonstrations** map onto gate behavior:
   - eligible verified task → reviewable candidate in the ledger (gate run on a real session);
   - failed/unverified task → skill archived (ledger shows reason, skill stays invisible to
     search);
   - duplicate probe: two extractions → second archived, first kept;
   - versioned update: `patch` on a kept skill produces versions[] head change;
   - new-session recall: live skill returned by `/skill/search` + raw load through the lane;
   - separate-agent isolation: proxy search filter drop-test (a private skill is absent from
     another agent's whitelist);
   - no duplicate extraction: single-buffer/single-worker design probe (conversation/add
     count + one archive point);
   - interruption recovery: kill a gate mid-run (flock + hash chain) and re-run;
   - regressions: existing suites (`memory-hook`, doc ingest, memory-promote tests, RepoQL
     doctor/run) all green.

## Gate implementation + first live demonstration (same day, addendum)

Delivered and verified on the .241 product checkout (`/home/bensl/singularity-repoql`):

- **`scripts/skill-gate.mjs`** — the verification gate: reviewer-class, demote-only,
  fail-closed. Lists active skills, fetches each record's detail (the list endpoint
  omits metadata), verifies `gate.evidence` provenance: every listed evidence file
  must exist on disk, every RepoQL query must hit (rql available), token-Jaccard
  dedup ≥ 0.8 against other active skills that themselves carry gate metadata
  (older copy stays; equal-timestamp ties break deterministically by skill id).
  VERIFIED → no write (ledger records the verdict). UNVERIFIED / DUPLICATE →
  idempotent soft-archive (POST /v3/skill/delete) with the reason recorded. Each
  run appends hash-chained outcome rows to `data/skill-gate/ledger.jsonl`;
  `verify-chain` detects tamper; a run refuses to summarize if its own chain check
  fails. Decisions are (skill_id, content_hash)-keyed: reruns skip decided skills
  (idempotency), dry-run writes nothing. No key material is printed or logged.
- **`scripts/skill-gate.test.mjs`** — 12 contract tests, all passing locally
  (bun) and on .241 (node --test): envelope enforcement, fail-closed verdicts,
  evidence-file misses, dedup semantics, archive via delete, dry-run no-writes,
  store-outage failure, secret hygiene, ledger chain + tamper detection,
  idempotency. Demo driver: `sg-demo.mjs` (repo root).
- **Live demonstration (store tdai-memory-core :8420)**: created the verified
  candidate `skl-n5H8pLSJ9H79` "onboard-extraction-provider-failover" with real
  gate.evidence (2 repo files) — kept ACTIVE. Created an auto-extracted-shaped
  twin without metadata — archived by the gate. A later identityless team-wide
  sweep archived all 10 remaining metadata-less records (6 were leftovers from
  the identity-contract probes). Final store state: exactly 1 active skill,
  gate-verified; ledger 11 rows (verified=1, unverified=10), chain ok=true.

### Store contract facts discovered (for the promotion-path integration)

- Create body needs the isolation ids as body fields (`team_id`, `agent_id`,
  `user_id`; `idFieldsShape`) — `x-tdai-*` header spellings are accepted by the
  strict-isolation middleware but the skill-create handler reads ids from the
  parse body; `owner_agent_id`/`agentId` etc. are stripped. `metadata` is the
  create key (NOT `metadata_json`); content must start with YAML frontmatter whose
  `name`/`description` match the body and whose name matches
  `^[a-z0-9][a-z0-9-]*$`.
- Quirk (upstream, worth reporting): skill/create persists the record (and its
  gate metadata) BEFORE `ensureSkillAsset`; when the owner agent is not
  registered in the metadata plane the binding fails with 50001, the HTTP
  response errors, but the record stays ACTIVE — i.e. a failed create can leave
  an untracked active skill. The gate fail-closed closes exactly this hole
  (all such records were archived in the sweep).
- The list endpoint returns pre-parsed `metadata` objects (SkillSummary), not
  `metadata_json` — the gate reads both.

### Remaining before full integration
